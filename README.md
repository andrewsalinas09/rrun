# rrun — zero-escaping remote & cross-shell execution

**Version 2.8.0** (core v2.5.0, ps shim v1.13, bash shim v1.10, hook v1.1) · Windows + WSL + any ssh-reachable host · ssh and adb targets

Run a script or command on any host, through any chain of shells (PowerShell ↔ Git Bash ↔ WSL ↔ ssh ↔ remote bash/PowerShell), **without writing a single escape character**. Payloads travel as base64 — inert in every parser — and are decoded only by the shell that executes them.

Born from an audit of 402 failed shell commands in Claude Code transcripts: the dominant self-inflicted failure classes were all interpreter-boundary escaping bugs. This repo fixes each class at the tool level instead of per-incident.

## The problem

Every interpreter layer eats one level of quoting. A command like

```
wsl bash -c 'ssh host "powershell -Command \"\$f = ...\""'
```

crosses four parsers; hand-counting which one consumes each `$` and `"` fails routinely:

| Failure class (audit count) | Symptom |
|---|---|
| WSL argv re-parsing (47) | `$VAR` silently expands to empty in the wrong shell (`cp: cannot stat '/rrun'`) |
| Heredoc corruption (20) | `unexpected EOF while looking for matching '` from CRLF/quote interplay |
| Nested `powershell -Command "$var"` (16) | outer shell interpolates `$var` away → `Missing expression after '='` |
| MSYS path mangling | `/home/x` rewritten to `C:/Program Files/Git/home/x` |
| cp1252 stdout (7) | `UnicodeEncodeError` the moment Python prints UTF-8 |
| CLIXML noise | `#< CLIXML ...` progress records polluting captured stderr |

## The principle

1. **Payload-as-data**: the script never appears inside a quoted string. It is base64-encoded (`[A-Za-z0-9+/=]` — no metacharacters exist), transported, and decoded by its executor: PowerShell natively via `-EncodedCommand` (UTF-16LE); POSIX shells via a **status-checked decode into a temp file** that the target shell then executes — `sh -c 't=$(mktemp) || exit 125; ... base64 -d > "$t" || { echo rrun: remote decode failed >&2; exit 125; }; <shell> "$t"'`. It is deliberately *not* a decode-and-pipe-into-the-shell one-liner: a pipeline reports the *shell's* status, so a missing/broken remote `base64` would feed the shell EOF and exit 0 while the payload never ran (fixed in 2.3.3), and file-backed execution keeps the payload's bytes and its real stdin intact (2.3.4).
2. **Per-layer re-armoring for multi-hop**: for `hostA,hostB` chains, each intermediate host runs `ssh next '<hop layer>'`, where the hop layer status-checks a base64 decode of rrun's *own next-layer command* and runs it via `exec sh -c` (`bash` is required nowhere; the decoded text is rrun's generated one-liner, never user payload bytes). The quoted part is pure base64, so quoting depth stays at one regardless of hop count.
3. **No shell re-parsing at the WSL boundary**: shims invoke `wsl.exe -e` (direct exec), so the WSL default shell never expands your argv.
4. **Streaming for large payloads, at any hop count**: a base64-embedded command can exceed a command-line limit — 8,191 chars via `cmd.exe` on stock Windows OpenSSH (capping embedded PowerShell payloads near 3 KB, since UTF-16LE+base64 is ~2.67× expansion), or 128 KiB per argv element on Linux, which nested hops reach fast because every layer re-armors the whole command (4/3 growth per hop). rrun composes both forms, measures the finished **outermost** command, and streams the base64 over stdin behind a small fixed bootstrap when it exceeds `RRUN_STREAM_LIMIT` (default 6000). Streaming works through nested chains too: each intermediate `ssh` forwards its stdin to the next hop, so only the innermost bootstrap consumes it and the composed command stays tiny regardless of payload size. If even the streamed form can't fit (`RRUN_MAX_CMD`, default 100000), rrun fails with advice to use `-J` rather than leaking `E2BIG`. Note that the limit counts *composed command* characters, not payload bytes, and it is the **outermost** command that gets measured (the binding constraint — every layer carries a command, and the outer one is the largest). So the payload size that actually trips streaming is well under the number, and shrinks with each hop. Measured crossovers per target shell and hop count are tabulated under **Caveats** below.

## Usage

```
rrun [-s ps|bash|sh|wsl] [-J jumphosts] [-n] <host[,hop2,...]|local|adb[:serial]> <script | - | -c "cmds">
```

| Flag/arg | Meaning |
|---|---|
| `-s ps\|bash\|sh\|wsl` | Target shell on the **final** host. Default `ps` (Windows targets); `*.sh`/`*.bash` scripts autodetect `bash`. Linux targets need `-s bash` (or a `.sh` file). `wsl` (2.9.0+) = **bash inside WSL on a Windows host**: the Windows side is crossed exactly like `ps` (an `-EncodedCommand` bootstrap no gateway shell can re-parse), then the bootstrap hands rrun's armored POSIX wrapper to `wsl.exe -e sh -c` as one native argument — `-s bash` against a Windows host would try to exec `bash` *on the Windows side* and fail. Needs WSL installed with a default distro for the ssh login user; a missing `wsl.exe` is a loud transport failure (stderr marker + exit 125). For host `local` on a Windows machine, `-s wsl` and `-s bash` are the same thing. Rejected for `adb` targets. |
| `-J jumphosts` | Native ssh ProxyJump — preferred for hops when your machine can auth straight to the final host. |
| `-n` | Dry-run: print the composed ssh invocation. |
| `host,hop2,...` | Nested-hop chain for when intermediate hosts hold the keys. Payload runs on the **last** host, and large payloads stream through the chain (2.3.7+). Hop names resolve per-hop (from the *previous* host's ssh config), and pre-existing known_hosts/keys are required at every link — rrun never auto-accepts host keys. Requirements are **position-dependent** (matrix-verified, 2.5.0): the *first* chain host only parses `ssh next '<quoted>'`, so it needs just an ssh client and a login shell that respects single quotes (csh/dash/busybox all fine); every host *after* the first — **including the final one** — executes the hop-decode layer and needs a POSIX-compatible login shell + `base64` + `sh` (`bash` is required nowhere since 2.5.0). Windows hosts cannot be *intermediate* hops (no `base64`/POSIX shell under `cmd.exe`); they are fine as the final target of a *single*-hop run. |
| `local` | Run the payload on this machine (shims only) — replaces every nested `powershell -Command "..."` pattern. |
| `adb[:serial]` | Run the payload on an Android device over `adb shell` instead of ssh (2.8.0+). Bare `adb` uses adb's own default device (it errors on 0 or 2+ attached); `adb:<serial>` targets one (`adb devices` lists them). Defaults to **`-s sh`** — stock Android has neither `bash` nor PowerShell — and `-s ps` is rejected outright. Legal **only as the last hop**: alone, the adb client runs on your machine; as the tail of a chain (`gw,adb:SERIAL1234`) it runs on the preceding host, so the device can hang off a different machine. `-J` is meaningless here (adb speaks USB/TCP, not ssh). |
| `script \| - \| -c` | Script file (Windows paths auto-translate to `/mnt/...`), stdin, or inline string. `-` means **raw OS stdin** — in the PowerShell shim that is deliberately *not* the PowerShell object pipeline (see caveats). An explicitly empty `-c ''` is a valid no-op program; only a *missing* `-c` argument is an error. |

```bash
rrun -s bash pi 'C:\path\to\diagnose.sh'   # Windows-pathed script on a Linux host
rrun winbox -c 'Get-Process | Sort CPU'    # PowerShell on a Windows host (default -s ps)
rrun -s wsl winbox -c 'uname -a; ls ~'     # bash inside the Windows host's WSL
rrun -s bash pi,sensor01 collect.sh        # two-hop: local -> pi -> sensor01
rrun -J pi -s bash sensor01 collect.sh     # same reach via ProxyJump (needs direct auth)
rrun local -c '$PSVersionTable'            # local PowerShell, no quoting hazards
echo 'uname -a' | rrun -s bash pi -        # payload from stdin
rrun adb -c 'find /sdcard -name "*.jpg"'   # Android device over adb (default -s sh)
rrun adb:SERIAL1234 scan.sh               # a specific device, script file payload
rrun gw,adb:SERIAL1234 -c 'getprop'       # device attached to a remote machine
```

**Caveats**:
- **Streamed** (large) payloads cannot read stdin — the channel carries the payload itself (`ps` and `bash`/`sh` alike, single-hop or nested). Non-streamed `bash`/`sh` payloads read the real ssh channel as of 2.3.3 (they used to read their own script text from the decode pipe). Payloads should still be non-interactive (`BatchMode=yes`).
- Tuning knobs: `RRUN_STREAM_LIMIT` (default 6000) is the embed→stream **threshold**; `RRUN_MAX_CMD` (default 100000) is the hard ceiling at which rrun refuses rather than leaking `E2BIG`. Both must be non-negative integers (bash arithmetic evaluates variable contents, so junk would otherwise surface as a confusing arithmetic error). Raising `RRUN_STREAM_LIMIT` (e.g. `30000`) keeps mid-size payloads off the streaming path on pwsh-`DefaultShell` Windows hosts — see the streamed-session race above.
- **`RRUN_STREAM_LIMIT` counts composed-command characters, not payload bytes, and it measures the *outermost* command** — so the payload size that actually switches you to streaming is much smaller than 6000, and shrinks with every hop (each layer re-armors 4/3; `ps` additionally pays ~2.67× for UTF-16LE+base64). Measured at the default:

  | Payload stays embedded up to | 1 hop | 2 hops | 3 hops |
  |---|---|---|---|
  | `-s bash`/`sh` | ~4.3 KB | ~3.1 KB | ~2.2 KB |
  | `-s ps` | ~1.5 KB | ~1.0 KB | ~0.7 KB |

  Crossing that line costs the payload its stdin, so check with `-n` when it matters: a streamed dry-run begins `printf %s <b64> | ssh`, an embedded one begins `ssh`. Measuring the outermost command is deliberate — it is the largest thing that has to fit, and measuring the final host's command instead is exactly what let a 74 KB payload die with `E2BIG` before 2.3.7.
- **In the PowerShell shim, `-` means raw OS stdin, not the PowerShell object pipeline.** `Get-Content x.sh | rrun -s bash pi -` does *not* feed those pipeline objects to rrun; the shim reads the raw process stdin handle (byte-for-byte transport requires it — an object pipeline re-encodes), which may block on a console. PowerShell has no `<` operator either (it is "reserved for future use"), and `cmd /c "rrun ... < x.sh"` does not work because `cmd` cannot resolve `rrun` → `rrun.ps1`. The form that does work from a PowerShell session redirects into the `powershell` process itself: `cmd /c 'powershell -NoProfile -Command "& rrun -s bash pi -" < x.sh'` (this is what the CI regression uses). From Git Bash/WSL, plain `rrun -s bash pi - < x.sh` works. Easiest of all: pass the file as the operand and skip `-` entirely. This cannot be auto-detected: `$MyInvocation.ExpectingInput` reads `True` for a raw `<` redirect as well as for a real pipeline, so a guard on it would reject the supported form.
- **rrun is transparent: payload exit codes pass through untouched and no code is reserved.** When the *transport itself* fails to decode the payload on the target (e.g. no `base64` there), rrun exits **125 and prints `rrun: ... decode failed` on stderr** — the stderr marker, not the number, is what identifies a transport failure (a payload is free to `exit 125` and that passes through like any other code). Single-hop targets are wrapped in `sh -c`, so csh/fish login shells are fine there; in a *chain*, hosts 2..N (final included) need a POSIX login shell + `base64` + `sh` — see the hop row above.
- **Exception to exit-code transparency, outside rrun's control: a PowerShell sshd gateway flattens non-zero exit codes to 1.** When the remote sshd's `DefaultShell` (Windows) or login shell (Linux pwsh) is PowerShell, the gateway runs the composed command via `-c`, which maps any failing native command to exit 1. Matrix-verified on Linux pwsh 7.4 **and, in the Windows-container lane, on real Windows PowerShell 5.1 and pwsh 7 behind real Windows sshd**: payload *output* arrives byte-perfect, success still exits 0, but `exit 5` comes back as 1. Since 2.7.0 this is **pinned as a CI assertion** (`exit 5 → 1` on both PowerShell editions, `exit 5 → 5` on cmd), so a future OpenSSH/PowerShell that restores fidelity flips the cell loudly instead of drifting from the docs. It is a PowerShell-gateway-family behavior, both editions. cmd.exe (the stock `DefaultShell`) and POSIX gateways preserve exact codes. If exact codes matter, don't put PowerShell behind sshd — or carry status in output.
- **Script-file operands are payload transport, not remote file staging.** `bash`/`sh` payloads execute from a trap-cleaned temp file on the target (`$0`/`BASH_SOURCE` point there, never at your original path; `ps` payloads run as an anonymous scriptblock — no `$PSScriptRoot`). Final `bash`/`sh` targets therefore need `mktemp` and `rm` alongside `sh` + `base64` (present on any ordinary Linux/busybox).
- **Known issue — Windows sshd streamed-session race**: streamed sessions to a Windows OpenSSH host can nondeterministically wedge *remotely* before the payload runs (the stuck `powershell.exe` sits at ~0.1 s CPU and the ssh channel never closes). Controlled A/B testing shows it is independent of rrun version, payload content, and payload success/failure — it is a host-side race in the sshd → shell → `powershell.exe` stdin chain, not an rrun quoting/transport bug. **Reproducible on demand since 2.6.0** in the Windows-container lane (`tests/matrix/matrix-win.ps1`), which measured it on **every** gateway — cmd.exe included (one run: 3/3 wedges on cmd, 2/3 on 5.1, 1/3 on pwsh) — so it is *not* specific to pwsh `DefaultShell` as earlier field observation suggested. Small (non-streamed) payloads are unaffected. Workarounds: wrap streamed calls in a timeout and retry (as `test.ps1` and the matrix lane do), or — if the remote `DefaultShell` is PowerShell, whose command line takes ~32 K chars instead of `cmd.exe`'s 8,191 — raise `RRUN_STREAM_LIMIT` (e.g. `30000`) so mid-size payloads avoid streaming entirely.
- `local` mode is bounded by the 32,767-char Windows process command line. The double encoding (payload → UTF-8 base64, embedded in a wrapper → UTF-16LE → base64) costs ~3.6 command-line chars per payload byte, so the practical ceiling is **~9 KB** of PowerShell payload; beyond that, use a file with `powershell -File`.
- PowerShell payload files are decoded by their BOM (UTF-8/16/32); **BOM-less files are treated as UTF-8**. Legacy ANSI-code-page scripts without a BOM will misdecode — save them with a BOM (or as UTF-8) first.
- **`adb` targets**: the device needs `sh`, `base64`, `mktemp` and `rm` — all present in Android's toybox since ~5.0. rrun pins `TMPDIR=${TMPDIR:-/data/local/tmp}` ahead of `mktemp` because `mktemp` is the wrapper's *first* statement and Android has no `/tmp`; a device that leaves `TMPDIR` unset would otherwise fail it and exit 125 with the payload never run. An existing `TMPDIR` is respected, not overridden. Large payloads stream over stdin (adb forwards it), same trade as ssh: the payload loses its own stdin. On Windows the shims run `adb.exe` directly rather than forwarding to WSL — the adb client and the USB device are both Windows-side and WSL2 has no USB passthrough. Note that `adb shell` writes the *device's* `stdout`/`stderr` interleaved onto one stream on older platform-tools; if you need them separated, redirect on the device.
- **`-s wsl` targets**: the payload runs under `bash` in the **default WSL distro of the ssh login user** on the Windows target (the decoded temp file lives inside WSL, `mktemp`/`rm`/`base64` come from the distro). Delivery is `ps`-shaped, so the `ps` caveats apply: a PowerShell sshd gateway flattens non-zero exit codes to 1 (cmd.exe preserves them — the bootstrap itself passes the payload's code back via `$LASTEXITCODE`), and streamed sessions to a Windows sshd can hit the wedge race above. Streamed `wsl` payloads ride an explicit PowerShell pipe into `wsl.exe` (the pipe appends a CR, which the wrapper strips before decoding — base64 is ASCII-safe under both editions' `$OutputEncoding`). **`wsl` payloads cannot read the ssh channel's stdin at all** — embedded or streamed, stdin reads see immediate EOF (measured on a real host: the PowerShell bootstrap layer does not forward its stdin to the unpiped `wsl.exe` child), unlike non-streamed `bash`/`sh` payloads on a Linux target. Comma-chains ending at a Windows host remain unsupported (the hop-decode layer needs a POSIX login shell on the *final* host, same as `-s ps` — see the hop row); use `-J` to reach a Windows+WSL box through hops. No WSL on the target → loud `rrun: wsl.exe not found on target` + exit 125, never a silent success.
- `BatchMode=yes` is always on — key auth only, no password prompts; rrun never auto-accepts host keys.

## Boundary advisory hook (Claude Code)

A tool only helps if it gets reached for. In practice the rrun rule gets skipped not from disagreement but because **the boundary-crossing is incidental to the goal** — you're thinking "grep a file in WSL" or "is the host up?", not "I am about to hand-quote three interpreters". A prose rule fires on noticing; this hook fires on the command's *shape*. It's the same move rrun itself makes: don't ask for careful escaping, remove the chance to get it wrong.

`install.ps1` wires it into `<claude-config>/settings.json` as a `PreToolUse` hook on `Bash|PowerShell`:

| It sees | It suggests |
|---|---|
| `wsl` + a POSIX shell (`-e bash`, `bash -c`, `bash -lc`) | `rrun -s bash local -c '...'` |
| nested `ssh … "ssh …"` | `rrun -s bash hop1,hop2 -c '...'` |
| `powershell`/`pwsh -Command` inside another shell | `rrun local -c '...'` |

- **Warn-only. It never blocks, and never emits a `permissionDecision`** — that's covered by a regression test, not just intent.
- **Escape hatch: put `# no-rrun` anywhere in the command.** This is load-bearing, not politeness: when rrun itself is broken, raw `wsl`/`ssh` is the only way to diagnose it, and a hard block would lock you out of repairing the tool. It also covers commands that merely *quote* these patterns (a commit message about rrun, `grep 'bash -c'`).
- **Dependency: Python 3.** The launcher fails *open* — no interpreter means silence, never a blocked command. Because that failure is invisible by design, `install.ps1` and `test.ps1` check for a working Python 3 and say so **loudly**; a silently inert guard is the exact failure class this repo exists to kill. `python3` is probed by *execution*, not by name: on Windows it's usually the Microsoft Store stub (on `PATH`, exits 49, "Python was not found").
- Don't want it? `.\install.ps1 -SkipClaudeHook`. Already installed and want it gone? Run `hooks\uninstall-hook.ps1 -ConfigDir <claude-config>` (or delete the entry via `/hooks` in Claude Code). Installer and remover both identify rrun's handler by **exact command identity** and filter handler-by-handler — other hooks survive even inside the same matcher group — and both back up to `settings.json.rrun-bak` only after the current file parses, so a corrupt `settings.json` can never overwrite the last good backup.
- Windows note: Claude Code runs `shell: bash` hooks under **Git Bash**, already an rrun prerequisite. Don't assume `bash` on `PATH` is it — under PowerShell that's usually `C:\WINDOWS\system32\bash.exe`, the *WSL launcher*, which can't resolve Windows paths (same family as the MSYS mangling gotcha below).

## Install

**Humans**: clone, then in PowerShell run `.\install.ps1` (add `-SkipClaudeHook` to skip the [advisory hook](#boundary-advisory-hook-claude-code)). Re-run any time — it's idempotent *and* self-updating (refreshes `~/.rrun/bash_env`, the `.bashrc` block contents, and its own `settings.json` hook entry). It finishes by running `test.ps1`, which needs no remote host; add `.\test.ps1 -TargetHost <host>` afterwards for real ssh round-trips including the streaming path, and `.\test.ps1 -TargetHops <a,b>` for a real nested chain (large-payload streaming through hops, md5-verified). `tests/core-tests.sh` runs the core against a mocked ssh on any Linux, and `tests/hook-tests.py` covers the advisory hook (both run in CI on every push, on Linux *and* Windows).

**Claude / AI agents**: point the agent at this repo and say "install this" — `CLAUDE.md` contains the exact steps and post-install rules of engagement.

**Linux-only hosts**: copy `bin/rrun` to `~/.local/bin/`, `chmod +x` — the core has no Windows dependencies.

## Changelog

- **2.9.0** (2026-08-19) — **WSL target shell (`-s wsl`): bash inside WSL on a Windows remote.** Found the usual way: `rrun -s bash andrew -c 'ls'` against a Windows host answered `The term 'sh' is not recognized...` — the POSIX branch tried to exec `sh` *on the Windows side*, and there was no way to reach a Windows host's WSL without hand-quoting the full `ssh → PowerShell → wsl.exe` stack, the exact boundary pile this tool exists to remove. The fix reuses both proven layers instead of inventing a third: the Windows side is crossed **exactly like `-s ps`** (a fixed PowerShell bootstrap rides as `-EncodedCommand`, inert under cmd/PowerShell/POSIX gateways — so multi-hop and `-J` compose with zero new machinery), and the bootstrap base64-decodes rrun's usual POSIX tempfile wrapper into a variable and hands it to `wsl.exe -e sh -c $__c` as **one native argument** — plain balanced quotes only, because nothing with `\"`-escaped quotes may cross a PowerShell native-argument boundary (the shim v1.12 / 2.4.3 lesson, now pinned for the core too); `bash` executes the payload inside WSL. Streamed payloads are piped **explicitly** (`[Console]::In.ReadToEnd() | wsl.exe ...`) rather than trusting handle inheritance across editions; the PowerShell pipe appends a CR, which GNU `base64 -d` rejects as garbage, so the wrapper strips `\r` ahead of the decode. A target without WSL fails loudly (`rrun: wsl.exe not found on target`, exit 125) — the guard exists because `exit $LASTEXITCODE` after a command-not-found would otherwise exit **0**, a silent success. Host `local` accepts `-s wsl` as an alias for `-s bash` in both Windows shims (this machine *is* the Windows host); `adb` targets reject it (Android has no WSL). - **2.8.0** (2026-08-11) — **adb transport**: `adb` / `adb:<serial>` as the final hop runs the payload on an Android device over `adb shell` instead of ssh. File/stdin sources are also encoded straight into base64 — the previous `$(cat)` capture stripped trailing newlines, so "byte-for-byte" is now literally true (`cmp`-verified in tests). **Hardening**: `install.ps1` passes the repo path to the WSL shell as positional data (`$1`) instead of interpolating it into shell source. **CI**: new `windows-latest` job runs the PowerShell shim's local mode with real `powershell.exe` (`tests/shim-local-tests.ps1`) — Windows semantics are now a merge gate, not just a manual suite.
- **2.2.1** (2026-08-10) — post-release review fixes. **Bug**: the large-payload ps streaming bootstrap rode as a bare `-Command iex(...)`; when the remote sshd's shell is PowerShell (`DefaultShell`, e.g. pwsh), that outer shell re-parsed the bootstrap — it evaluated the parenthesized subexpression itself and re-quoted the payload through a second `-Command` layer, silently corrupting `$`-bearing statements (verified against a real pwsh-DefaultShell host; stock `cmd.exe` sshd passed it through unharmed). The bootstrap now travels as `-EncodedCommand`, inert under cmd, PowerShell, and POSIX shells. **Hardening**: host tokens starting with `-` rejected (ssh would parse them as options); dry-run `%q`-quotes every ssh argv element (metachar `-J` args printed unquoted); PowerShell shim rejects `local -c` with no command (was a silent empty success). **Tests**: bootstrap-inertness and option-shaped-host regressions in `core-tests.sh`; `test.ps1 -TargetShell ps` now does a real large-payload streaming round-trip against a Windows host, and a no-remote-needed gateway-emulation section pipes a `$`-bearing probe through the composed command under all three sshd shells (cmd.exe, PowerShell 5.1, pwsh 7) exactly as sshd would invoke them.
- **2.2.0** (2026-08-10) — external-review fixes. **Bugs**: `-n local` no longer *executes* the payload (dry-run safety); `-c` arguments are opaque — only the script-source operand gets Windows→`/mnt` translation (previously `-c ./deploy.sh` could be rewritten to a local `/mnt/...` path). **Transport**: automatic stdin-streaming for payloads whose composed command exceeds `RRUN_STREAM_LIMIT` (default 6000; Windows `cmd.exe` 8191-char ceiling), fail-fast with `-J` advice for oversized nested-hop ps targets. **Hardening**: host tokens validated (only payload is armored; hop names are interpolated), `-s` validated in core and shims, missing-optarg errors, `cat --`, `%q` paste-safe dry-run output. **Install**: `BASH_ENV` now points at dedicated `~/.rrun/bash_env` (tiny, always refreshed; migrated automatically from the old `.bashrc` target); `.bashrc` marker block *replaced* on rerun, `.bash_profile` repaired if it doesn't source `.bashrc`; installer verifies via the full test suite. **CI**: mocked-ssh core regression suite (`tests/core-tests.sh`) on every push.
